# Product Brief — Shared Shopping List

## One-line summary

Shared Shopping List is a minimal Android + backend app for managing a shared grocery list, built as a hands-on portfolio demo of mobile/backend integration, tests, and CI/CD.

## Target outcome

A reviewer or interviewer should be able to see a complete small product delivery loop:

1. Start the backend locally.
2. Open the Android app.
3. Create a list such as `Weekend groceries`.
4. Add items such as milk, bread, and apples.
5. Mark an item as bought.
6. Refresh or restart the app.
7. See persisted state from the backend.
8. Review GitHub Actions checks for backend tests, Android build/tests, and Docker build.

## Users and scenarios

### Primary user

A person who wants a simple shared grocery list for a household.

### Portfolio reviewer / interviewer

A hiring manager, engineering lead, or QA lead who wants to see how Alexander structures a small full-cycle product demo.

Expected value:

- simple feature scope is easy to understand;
- implementation touches mobile, backend, tests, and CI/CD;
- demo can be shown in a few minutes;
- test and build pipeline can be discussed directly.

## Core workflow

1. User creates a shopping list.
2. User adds items with optional quantity.
3. User marks items as bought while shopping.
4. User can rename or remove items.
5. Another person can open the same list by ID or link in a later version.

## MVP capabilities

### Shopping lists

- Create list.
- Get all lists.
- Get one list with items.

### Shopping items

- Add item to list.
- Update item name.
- Update quantity.
- Toggle bought / not bought.
- Delete item.

### App behavior

- Loading state.
- Empty state.
- Error state.
- Pull-to-refresh or explicit refresh.

## Technology proposal

### Backend

- Python.
- FastAPI.
- SQLite.
- SQLModel for the MVP.
- pytest.
- Docker.
- Docker Compose.
- OpenAPI generated by FastAPI.

### Android

- Kotlin.
- Jetpack Compose.
- Retrofit REST client.
- ViewModel.
- Coroutines / Flow if useful.
- Unit tests for ViewModel and API mapping.

### CI/CD

- GitHub Actions.
- Backend lint and tests.
- Backend Docker build.
- Android unit tests.
- Android Gradle build.
- APK artifact upload.
- Optional OpenAPI schema artifact.

### Hosting

- Local development on MacBook Pro M1.
- Backend hosted on the VPS through an isolated Docker Compose app.
- Public endpoint or subdomain to be decided before remote mobile demo.
- `/health` endpoint and smoke check required before calling the deployment ready.

## Quality strategy

The project should demonstrate quality through the development workflow, not through a complex product domain.

Minimum checks:

- backend API tests for happy paths and validation errors;
- backend 404 behavior for missing list/item;
- Android ViewModel tests for loading, toggling, and error state;
- CI checks that run on every pull request;
- repeatable local run instructions;
- clear demo scenario in README.

## Non-goals

- Authentication and user management.
- Real-time collaboration.
- Managed backend-as-a-service implementation through Firebase or Supabase.
- Complex offline support.
- Payment, barcode scanning, recipes, or grocery catalogs.
- Production-grade UI polish.

## Success criteria for MVP

- Backend can be started locally with Docker Compose or a simple command.
- Android app can talk to the backend in local/dev mode.
- Android app can talk to the VPS backend in demo mode once deployment is ready.
- User can create a list and manage items.
- Backend tests pass in CI.
- Android build and unit tests pass in CI.
- A demo APK artifact can be produced.
- Deployed backend passes `/health` and basic API smoke checks.
- README explains why the project exists and how to demo it.
